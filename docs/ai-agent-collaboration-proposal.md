# Cursor·Antigravity 저장소 협업 제안 — 검토 요청

**상태:** 제안만 담은 draft PR. 구현은 Cursor와 Antigravity의 검토 및 사용자 승인 전까지 하지 않는다.

## 문제

현재 Cursor와 Antigravity가 각각 별도 명령으로 작업하고 PR을 만들면 코드 변경, 근거, 반론이 여러 브랜치와 대화에 갈라진다. 같은 변경을 두 PR에서 반복하거나, 한 모델이 다른 모델의 최신 판단과 저장소 맥락을 놓치기 쉽다. 사용자는 두 모델 사이에서 내용을 옮기는 조정자 역할까지 맡게 된다.

## 저장소에서 확인한 기존 맥락

- `AGENTS.md`는 이슈별 작업과 승인 후 코딩을 요구한다.
- `.cursor/HANDOFF.md`는 현재 제품 결정과 `main` 상태를 요약한다.
- `operating_rules.md`에는 멀티플랫폼·운영 안전 기준과 과거 AI 간 상호 협약이 있다.
- `docs/ai-work-log-and-app-chrome-2026-11-12.md`는 앱 내부 `dev-ai-council`이 브랜치/PR/파일 변경을 보지 못한다고 명시하고, 앱 의회를 PR 도구로 확장하지 않기로 했다.
- `docs/access-policy.md`, 도메인 SSOT, 테스트/QA 가이드와 GitHub PR·커밋 기록이 추가 근거다.

따라서 제안은 앱의 AI 의회를 수정하거나 새 비용이 드는 클라우드 AI 서비스를 붙이는 것이 아니다. 저장소 기록을 공통 맥락으로 사용해, Cursor와 Antigravity가 같은 코드 변경과 PR에서 협업하는 개발자 도구를 검토하는 것이다.

## Copilot의 초안 의견

1. **단일 브랜치·단일 PR:** 한 에이전트가 변경을 만들고, 다른 에이전트가 같은 변경의 리뷰어가 된다. 토론을 위해 두 번째 PR을 만들지 않는다.
2. **공통 지침:** Cursor와 Antigravity가 함께 읽을 수 있는 Agent Skills를 저장소에 둔다. 후보는 `safenex-agent-debate`(토론 절차), `safenex-change-safety`(운영·승인·배포 경계), `safenex-permissions-and-rls`, `safenex-supabase-migrations`다. 현재 SSOT를 복제하지 않고 링크·검증 절차를 제공한다.
3. **기존 로컬 도구 우선:** 가능하다면 사용자 PC에 로그인된 Cursor 및 Antigravity CLI를 한 번의 로컬 명령으로 순차 호출한다. Cursor 의견 → Antigravity 반론 → 재검토 → 합의/미해결점으로 제한하고, 최종 결과만 같은 PR 댓글로 남긴다. 예비 후보 명령은 `agent -p` 및 `agy -p`다.
4. **안전 경계:** 코드 리뷰 전용이며 파일 수정, 프로젝트 코드 실행, 커밋, 푸시, 승인, 병합을 자동화하지 않는다. CLI 권한 프롬프트를 우회하지 않고, 토론 횟수도 고정한다.
5. **비용·인증:** 외부 API 키, GitHub Actions 모델 호출, 별도 호스팅 서비스를 새로 요구하지 않는다. 기존 로컬 로그인으로 가능한지, 기존 요금제의 사용량 안에서 동작하는지는 각 에이전트가 공식 사용법과 사용자 환경을 기준으로 검증해야 한다. “별도 API 요금 없음”과 “사용량 무제한”은 같은 말이 아니다.
6. **기록 재사용:** `AGENTS.md`, HANDOFF, 운영 규칙, AI 작업 로그, 접근 정책 및 관련 PR/커밋을 공유 컨텍스트로 한다. 전체 기록을 매번 프롬프트에 무차별 복사하지 않고, 현재 이슈와 관련된 기록을 찾아 포함한다. IDE 내부 채팅 기록은 저장소에서 자동 접근 가능하다고 가정하지 않는다.

## Cursor와 Antigravity에 요청하는 검토

각 에이전트는 이 제안에 독립적으로 의견을 남겨 주세요. 이 단계에서는 구현하지 말고, 근거와 함께 아래 질문에 답해 주세요.

1. 위 목표를 추가 API 키·호스팅 비용 없이 로컬에 이미 로그인된 도구로 달성할 수 있는가? 현재 공식 CLI 명령, 인증 방식, 사용량 제한을 확인해 주세요.
2. 두 IDE/CLI가 공통으로 발견하는 지침·스킬의 정확한 경로는 어디인가? `.agents/skills/`와 `AGENTS.md`가 양쪽에서 같은 동작을 하는지 확인해 주세요.
3. 한 번의 실행으로 두 모델을 차례로 부르고 같은 PR에 안전하게 결과를 남기는 것이 가능한가? 실제 GUI 세션 재사용, CLI 별도 세션, 단순한 공통 PR 댓글 절차 중 무엇이 맞는지 비교해 주세요.
4. 로컬 실행기가 PR diff의 지시문을 처리할 때 발생할 수 있는 프롬프트 인젝션·명령 실행·인증정보 접근 위험을 어떻게 제한해야 하는가?
5. 기존 문서와 과거 결정 중 제안과 충돌하는 항목이 있는가? 특히 앱 내부 AI 의회와 저장소 PR 토론을 혼동하지 말아 주세요.

## 합의 및 완료 기준

- 먼저 양쪽 모델이 이 제안에 댓글로 리뷰와 반론을 남긴다.
- 사용자와 합의한 뒤에만 구현한다. 반대 의견이 남으면 숨기지 말고 선택지와 영향을 제시한다.
- 구현안은 실제 사용자 PC의 기존 로그인으로 재현 가능해야 하며, 별도 API 키나 유료 서버가 필수면 이 제안의 조건과 맞지 않는다고 명시한다.
- 동일 PR 하나에서 변경·리뷰·토론 기록을 추적할 수 있고, 스크립트가 실패하거나 파일이 바뀌면 성공처럼 보고하지 않아야 한다.
