## 공통 원칙 (모든 항목에 적용)

- 딱 명시된 파일/범위만 수정한다. 관련 없어 보이는 다른 파일은 절대 건드리지 않는다.
- 새로운 추상화, 새로운 라이브러리, 새로운 패턴을 도입하지 않는다 — 기존 코드 스타일/패턴을 그대로 따른다.
- 안전 관련 로직을 완화하는 방향으로 절대 바꾸지 않는다. 애매하면 더 안전한 쪽으로 판단한다.
- DB는 기존 마이그레이션 파일을 수정하지 말고 `supabase/migrations/`에 새 타임스탬프 파일(`YYYYMMDDHHMMSS_설명.sql`)을 추가한다.
- 작업 끝나면 diff를 요약해서 보여주고, 확인 전까지 커밋/푸시하지 않는다.

## TRACK A — 보안 영향 있음, 우선 처리

### A3. RLS `company_id IS NULL` 회귀 수정

`can_access_company_data` 함수(가장 최근 정의는 `supabase/migrations/20260805010000_fix_rls_null_company_write.sql`)를
확인한다. 이 함수는 `company_id`가 NULL인 행에 대해 무조건 `true`(전체 공개)를 반환하는데,
이러면 회사 구분 없이 모든 프로젝트 멤버가 열람 가능해진다.

`work_permits` 테이블은 이미 이 NULL 케이스를 더 안전하게 처리하고 있다
(`supabase/migrations/20260730100000_fix_gc_peer_isolation.sql` 약 140-157줄 참고 —
발주처/master 역할로만 제한). `can_access_company_data`도 같은 패턴을 적용해서,
`company_id`가 NULL이면 무조건 허용하지 말고 발주처(owner 계열)/master 역할에게만
허용하도록 새 마이그레이션으로 재정의한다.

기존 `CREATE OR REPLACE FUNCTION public.can_access_company_data(...)` 시그니처와 이름은
그대로 유지한다(호출부를 안 바꾸기 위해).

작업 후: 새 함수 정의 SQL 전문을 보여줘.

### A4. AI 생성 비용/호출 상한

기존 재시도/폴백 로직 자체를 없애지 말고, 그 위에 상한선만 추가한다.

위험성평가 AI 생성 경로(`src/lib/riskAutoGenAI.ts`의 재시도 로직 — `withRetry` 및 관련 호출부,
`supabase/functions/generate-risk-ai/_shared/nvidiaChat.ts`의 모델체인/모델당 재시도 로직)를 보면
클라이언트 재시도 × 모델체인 × 모델당 재시도가 곱해져서 행 하나당 이론상 최대 24회까지
LLM 호출이 발생할 수 있는 구조다. 토큰/비용을 어디에도 기록하지 않는다.

수정 방향:
1. 전체 생성 요청(행 하나 또는 배치 하나) 단위로 총 LLM 호출 횟수 상한을 하나 추가한다.
   상한에 도달하면 그 이상 재시도하지 않고 실패로 명확히 처리한다(조용히 무한 재시도 금지).
2. `nvidiaChat.ts`의 응답에 이미 포함된 `usage`(토큰 사용량, 약 263줄)를 최소한 `console.log`로
   남긴다 — 별도 테이블/대시보드까지는 만들지 말고, 지금은 로그로 남기는 것까지만 한다.

작업 후: diff와, 상한값을 몇으로 잡았는지 이유와 함께 설명해줘.

### A5. AI 재시도실패 텍스트가 위험성평가 레코드에 저장되는 문제

`src/lib/riskAutoGenJob.ts`의 `markRowFailed`(약 380-392줄)가 실패 사유 문구
("API 과부하로 생성 지연. [재시도] 버튼을 눌러주세요" 등)를 `hazard` 필드에 그대로 저장한다.
`hazard`는 위험성평가서에 실제로 인쇄/결재되는 필드라서, 실패 문구가 정식 위험요인으로
노출될 수 있다.

수정 방향:
1. 이 행에 실패 상태를 나타내는 별도 필드/플래그를 세팅한다(이미 있는 status류 컬럼이
   있으면 그걸 쓰고, 없으면 최소한으로 하나 추가한다 — 새 테이블/큰 스키마 변경은 하지 않는다).
2. `hazard` 필드 자체에는 에러 문구를 넣지 않는다. UI(위험성평가 목록/편집 화면)에서 이
   실패 상태인 행은 시각적으로 구분되게 하고, 이 상태인 채로는 결재/제출이 안 되도록
   막는다(기존 제출/결재 로직에 이 상태 체크만 추가 — 제출 로직 자체를 새로 만들지 않기).

작업 후: diff와 실패 케이스를 재현했을 때 UI가 어떻게 보이는지 설명해줘.

### A6. AI 포지셔널 폴백 오매칭

`src/lib/riskAutoGenJob.ts`의 `matchFilledToDraft`(약 441-457줄)에서, AI가 생성한 상세
내용을 원본 항목과 매칭하지 못했을 때 순번(포지션)으로 강제로 끼워맞추는 폴백이 있다.
이러면 세부작업과 안전대책이 서로 안 맞는 행이 만들어질 수 있다.

수정 방향: 매칭 실패 시 순번으로 끼워맞추지 말고, 그 행은 미완성/실패 상태로 남긴다
(A5에서 추가한 실패 상태 필드를 그대로 재사용). 사용자가 그 행만 재생성하거나
수동으로 채우도록 UI에서 유도한다 — 자동으로 잘못된 값을 채워넣지 않는 것이 핵심이다.

작업 후: diff를 보여줘.

## TRACK B — 실서비스 전환 전 처리 (지금은 테스트 기간이라 급하지 않음)

### B1. 작업허가서/TBM 하드삭제 방지

`src/pages/Trash.tsx`(약 146줄)의 휴지통 영구삭제 기능이 `work_permits`, `tbm_sessions`
테이블에도 적용되는데, `tbm_sessions`는 `tbm_participations`가 `ON DELETE CASCADE`라서
서명된 참석 기록까지 같이 영구 삭제된다. 지금은 테스트 기간이라 급하지 않지만
실서비스 전환 전에 반드시 막아야 한다.

수정 방향: `work_permits`, `tbm_sessions`는 이 파일의 삭제 대상 목록에서
제외한다(하드 삭제 자체를 막는다). 다른 테이블(테스트/임시 데이터 성격이 강한 것들)의
기존 삭제 동작은 그대로 둔다. 소프트삭제로 전환하는 큰 작업은 지금 하지 말고,
일단 이 두 테이블만 하드삭제 경로에서 빼는 것으로 범위를 좁힌다.

작업 후: diff를 보여줘. 이 두 테이블을 뺀 후 휴지통 화면에서 실수로 지운
허가서/TBM을 복구할 방법이 필요하면 알려달라고 말해줘(범위 밖이라 이번엔 안 만듦).

### B2. 승인 상태머신 이원화 — 레거시 경로 에러 핸들링만 우선

기존 두 승인 경로(레거시 버튼 / 결재선) 중 어느 쪽을 없앨지는 별도로 결정할
사안이니 이번엔 건드리지 말고, 레거시 경로의 에러 처리만 고친다.

`src/pages/WorkPermits.tsx`의 `submit()`(약 444줄), `review()`(456줄), `approve()`(467-478줄),
`reject()`(499줄) 4개 함수가 모두 supabase update 호출의 에러를 받지 않고 무조건
"성공" 토스트를 띄운다. RLS 거부나 DB 에러가 나도 사용자는 성공한 줄 안다.

수정 방향: 4개 함수 모두 `{ error }`를 받아서, 에러가 있으면 실패 토스트를 띄우고
성공 토스트를 띄우지 않는다. 그 외 로직(상태 전이 조건 등)은 전혀 건드리지 않는다.

작업 후: diff를 보여줘.

### B3. work_permits.status DB 제약 추가

`work_permits.status` 컬럼에 CHECK 제약이 없어서 임의 문자열이 들어갈 수 있고
(실제로 '승인'/'승인완료'/'발행완료'/'APPROVED'/'ISSUED'/'approved' 등 여러 표기가
섞여 있는 것으로 확인됨), 락 트리거 `enforce_work_permit_edit_lock`(가장 최근 정의는
`supabase/migrations/20260803020000_link_work_permit_tbm.sql` 약 33-51줄)이
`form_data`/`signatures`/`work_name` 등은 잠그지만 `status`/`approved_by`/`approved_at`은
잠그지 않아서, `created_by = auth.uid()`인 UPDATE RLS 예외(`20260730100000_fix_gc_peer_isolation.sql`
약 184-190줄)와 합쳐지면 작성자 본인이 자기 허가서 status를 '승인'으로 직접
바꿀 수 있다.

수정 방향: 새 마이그레이션에서
1. `status`에 허용 가능한 실제 값 목록으로 CHECK 제약을 추가한다(현재 코드에서 실제로
   쓰는 문자열들을 먼저 grep해서 빠짐없이 포함시킨다 — 값을 추측하지 말고 코드에서
   확인한 것만 넣는다).
2. `enforce_work_permit_edit_lock` 트리거 함수를 `CREATE OR REPLACE`로 재정의해서,
   일반 작성자(`created_by = auth.uid()`)가 `status`/`approved_by`/`approved_at`을
   직접 바꾸려 하면 막는다. 결재선/관리자 경로를 통한 정상적인 승인 흐름은
   막지 않아야 한다 — 어떤 role/조건으로 정상 승인이 이뤄지는지 기존 결재선
   코드(`approvals` 테이블 관련)를 먼저 확인하고 그 경로는 허용하도록 조건을 짠다.

작업 후: 새 마이그레이션 SQL 전문을 보여줘.

### B4. tbm_sessions RLS 회사 스코프 추가

`tbm_sessions`의 RLS 정책이 2026-05-06 원본 이후 한 번도 갱신되지 않아서, 회사 구분 없이
`is_project_member()`만 통과하면 프로젝트 멤버 전원이 다른 협력사의 TBM 세션까지
열람/수정할 수 있다.

`work_permits`는 이미 `can_access_company_data` 기반으로 회사 스코프가 적용돼 있다
(가장 최근 정의는 `supabase/migrations/20260730100000_fix_gc_peer_isolation.sql` 참고).
`tbm_sessions`의 SELECT/UPDATE 정책도 새 마이그레이션으로 재정의해서 같은
`can_access_company_data` 함수를 재사용해 회사 스코프를 적용한다. `tbm_participations`에도
같은 문제가 있는지 확인해서 있으면 같이 고친다. INSERT 정책과 마스터/관리자
전체열람 예외는 유지한다.

작업 후: 새 마이그레이션 SQL 전문을 보여줘.

### B5. crew sync 3중 구현 통합

`src/lib/permitCrewSync.ts`, `src/lib/syncPermitCrewFromTbm.ts`, `src/lib/syncPermitCrewToTbm.ts`
세 파일이 각각 `work_permit_workers`/`tbm_participations`에 대해 delete-then-insert를
트랜잭션 없이 수행한다. insert가 실패하면 delete만 반영돼서 명단이 빈 채로 남을 수 있다.

수정 방향: 세 파일의 delete-then-insert 로직을 하나의 Postgres 함수(RPC)로 옮겨서
트랜잭션 안에서 delete+insert가 원자적으로 실행되게 한다(하나라도 실패하면 전체
롤백). 세 파일은 이 RPC를 호출하는 얇은 wrapper로만 남기고, 각 파일 고유의
호출 조건/가드 로직(예: `shouldRefuseEmptyCrewReplace` 같은 것)은 RPC 호출 전 체크로
그대로 유지한다 — 그 가드 로직 자체는 새로 만들지 말고 기존 것을 그대로 옮긴다.

작업 후: 새 마이그레이션(RPC 정의)과 세 파일의 diff를 보여줘.
